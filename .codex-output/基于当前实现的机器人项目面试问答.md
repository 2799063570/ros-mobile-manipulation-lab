> [!warning] 先统一这七个口径
> 1. **底盘使用自定义固定长度协议和 BCC 异或校验，不是 CRC16，也不是 Modbus。**
> 2. **ros_control 轨迹队列是 `moodycamel::ReaderWriterQueue`，约束为 SPSC；视觉伺服 `CommandQueue` 是 `mutex + deque`。**
> 3. 当前独立 PBVS 默认支持 `on_demand_output=true`：50 Hz 更新速度目标，200 Hz 按需平滑生成点，不经过位置 FIFO；混合规划保留轨迹回放路径。
> 4. 当前 ros_control 固定 200 Hz／5 ms 轨迹采样，不能把它与 50 Hz 视觉闭环混为一谈。
> 5. 六轴状态整体一致性由反馈互斥锁保证；六个 `atomic<double>` 本身不构成一个原子快照。
> 6. 底盘已有串口异常重连、重连先发零速及 `/cmd_vel` 超时停车；尚不能据此声称具有完整的“有效状态帧超时检测”和 MCU 端失联保护。
> 7. 未在本仓库找到 STM32 固件及题目引用的《陈赛-软件开发(2).pdf》。DMA、1 ms、前馈 PID 的具体实现和个人贡献需另补证据。

## 二、根据简历整理的项目面试题

### 项目一：AUBO i5 机械臂智能分拣与视觉伺服系统（P0）

#### 1. 机械臂驱动与 ros_control

##### A01｜如何将 AUBO 厂商 SDK 封装成 ROS 驱动？

【实现】我把 SDK 的连接、启动、状态获取和轨迹发送封装在 `AuboHardwareInterface` 中，继承 `hardware_interface::RobotHW`，注册六轴的 `JointStateInterface` 与 `PositionJointInterface`。主循环运行 `read → controller_manager.update → write`；`write()` 只生成和入队位置点，独立喂点线程查询控制柜 MAC 缓冲并调用 SDK 发点。

连接也按用途分离：发送管理、状态诊断、MAC 查询与发点，另有独立只读反馈查询连接，避免所有操作争抢同一连接。**不要只说“双连接”**，当前类已不止两个 SDK 对象。源码见 S1、S2。

##### A02｜ros_control 的作用是什么？RobotHW 需要实现什么？

【实现＋原理】它将控制器算法与硬件通信解耦：上层控制器读状态、写命令，不直接调用厂商 SDK。`RobotHW` 注册关节句柄，将接口绑定到状态数组和命令数组；本项目实现初始化、`read()`、`write()`、`doSwitch()` 及关闭逻辑。`controller_manager` 管理控制器生命周期、资源占用和周期更新。控制器不是硬件通信驱动，MoveIt 也不直接等于 ros_control。

##### A03｜关节状态怎么读，位置指令怎么发？

【实现】反馈可来自 SDK 路点推送或独立轮询，更新带时间信息的状态缓存；`read()` 在反馈锁内把六轴位置、速度和力矩缓存复制到控制器使用的数组。位置命令由控制器写入 `joint_position_cmd_`，经过有限值等检查后入 SPSC 队列，再由消费线程批量发送到 TCP2CANBUS。反馈超时会阻止继续运动；缓存频繁被读取不代表硬件产生了新采样。

##### A04｜MoveIt 轨迹如何传递给机械臂控制器？

【实现＋原理】标准执行链路为：`MoveGroup → 轨迹执行管理 → FollowJointTrajectory Action → 关节轨迹控制器 → PositionJointInterface → RobotHW::write → SDK → 控制柜`。控制器按采样周期插值，硬件接口负责把采样点送到设备。需核对 Action 名称、关节顺序、时间戳和容差配置。

本仓库还有另一条**混合控制路径**：向 MoveIt 请求规划结果，在视觉伺服节点内验证并回放，最终走该节点的执行后端。回答前先说明演示使用哪条路径，不能把所有规划都说成经过 JTC。见 S1、S4、S5。

##### A05｜SDK 发送阻塞时，怎么保证其他线程工作？

【实现】把发点放在独立线程，反馈与 MAC 通道按职责分离，ROS 回调由 `AsyncSpinner` 处理；共享数据锁只覆盖短时间的读写，尽量不包住 SDK 调用。这样一个发送调用慢下来时，其他不依赖该调用或同一把锁的线程仍有机会运行。

**边界：**独立线程不能消除 SDK 内部全局锁，也不能保证永久阻塞后可正常 `join()`。仍需传输超时、反馈新鲜度检查、积压限制和停止确认；如果 SDK 不支持有界取消，可考虑进程隔离。【改进】不能宣称“多线程保证绝不阻塞”。

#### 2. C++ 并发与线程架构

##### A06｜为什么用独立发送线程，不直接在回调中发送？

【实现】SDK 网络调用耗时不稳定，直接写在回调或 5 ms 控制循环中会传播延迟。生产端只做状态检查和入队，发送线程负责设备水位、批量发点和错误处理，形成背压边界。代价是多了队列延迟和生命周期管理，因此需要监控队列长度、最旧命令年龄、发送耗时及控制柜余量。

##### A07｜无锁队列是 SPSC、MPSC 还是 MPMC？为什么？

【实现】ros_control 中使用 `moodycamel::ReaderWriterQueue<QueuedCommand>`，是 **SPSC**：主控制循环唯一生产，喂点线程唯一消费。ROS 回调不能同时作为第二生产者直接写这个队列；清理、查看队头等操作也必须遵守库的端点约束。

视觉伺服的 `CommandQueue` 是有锁容器；当前独立 PBVS 的按需输出路径则不经过位置队列。**“项目用了无锁队列”不等于“所有队列无锁”。**

##### A08｜队列满了怎么办？是否丢弃旧指令？

【实现】分数据语义处理：

|路径|满载策略|理由|
|---|---|---|
|ros_control 的定时轨迹点|生成前背压；达到异常积压上限或入队失败则锁定停止|每点代表 5 ms，丢点会改变轨迹时间与运动约束|
|保留的视觉伺服 `CommandQueue`|满时弹出最旧未执行点，再加入新点|强调修正的新鲜度，但仍要靠后端限速和连续性检查|
|当前独立 PBVS 按需流|更新速度目标，再按设备所需容量生成平滑点|避免位置 FIFO 中积累过期修正|

即便两个轨迹点位置相同，也不能随意去重，它可能表示保持时间。队列目标水位和异常硬上限不是同一概念。见 S2、S3、S6。

##### A09｜原子状态缓存怎么实现？多个关节属于同次采样吗？

【实现】缓存包含 `array<atomic<double>, 6>`，但 `read()` 和 `updateFeedbackAt()` 都使用 `feedback_mutex_`，把整组六轴复制作为临界区。单轴原子性只保证一个数不被撕裂，不能保证逐个读取的六个值来自同次回调；整体一致性来自这把锁。

此处 `relaxed` 可以用于锁内的单值访问，跨字段同步由互斥锁提供。`atomic<double>` 是否底层无锁也与平台有关，不能把“atomic”直接等同于“无锁”。见 S2。

##### A10｜AsyncSpinner 与 ros::spin() 有什么区别？

【实现＋原理】`ros::spin()` 在调用线程里阻塞处理回调，通常串行执行该回调队列；`AsyncSpinner(N)` 用后台线程处理回调，调用线程可以执行控制主循环。当前硬件节点是 2 线程 spinner，视觉伺服为 3，分拣核心为 4。

多线程会允许不同回调并发，因此目标、关节状态、控制状态仍需同步。同一订阅的回调是否可并发还受 roscpp 订阅选项影响，不能简单说“N 个线程让每个回调都同时执行”。

##### A11｜初始化、目标管理、抓取执行为什么拆线程？怎么回收？

【实现】`SortingTask` 将等待控制器等初始化工作、连续目标处理和较长的规划抓取操作分开，使接收检测、停止请求和状态发布保持响应。连续分拣启用时才启动目标线程；执行操作前也管理旧线程的回收。

析构先关闭相关输入，设置目标线程退出标志并 `notify_all()`，设置停止标志，调用机械臂停止、取消夹爪目标，再对初始化、操作、目标线程逐一检查 `joinable()` 并 `join()`。**join 是等待退出，不是强制终止**；有阻塞外部调用时仍要审查退出时间。见 S7。

#### 3. 视觉伺服与业务控制

##### A12｜50 Hz 视觉伺服怎么实现？为什么选 50 Hz？

【实现】默认 `control_rate=50`，ROS 定时器约每 20 ms 读取目标和关节快照，计算位姿误差，通过雅可比阻尼伪逆得到关节速度，并做限速、限加速度和限位处理。默认 `output_rate=200`；当前按需路径按 5 ms 生成平滑轨迹点，还约束 jerk。

【解释】50 Hz 是视觉更新、计算负载、通信延迟与闭环带宽的工程折中，不是相机一定 50 FPS，也不是实时性证明。应拿实际输入帧率、端到端延迟和控制回调周期分布说明选择，不能仅凭参数断言系统稳定运行在 50 Hz。见 S3、S6。

##### A13｜识别、位姿估计、规划、执行如何传数据？

【实现】感知侧把图像检测与 RGB-D 几何结合，发布 `DetectedObjectArray` 等目标信息，伺服侧也接收 `PoseStamped` 目标。业务层关联多帧目标、确认实例与预留目标，运动模块依据统一坐标系中的目标构造抓取位姿，规划后交给执行路径。时间戳、`frame_id`、类别、置信度和实例状态都重要，不能只传三个浮点数。

当前目标实例 ID 由分拣实例缓存维护，不应假定是 YOLO 自动给出的持久物体 ID。跨节点共享依靠消息和服务，不是共享 C++ 指针。见 S8、S9。

##### A14｜规划运动与视觉伺服怎样切换并互斥？

【实现】混合控制节点以状态机管理远距离规划回放和近距离 PBVS，进入／退出距离设有滞回，控制状态由 `control_mutex_` 保护，规划请求还需避免过期结果重新生效。`hybrid_control.cpp` 的默认进入距离为 0.10 m、退出距离为 0.16 m，启动配置可以覆盖。

跨进程运动写入还有 `MotionLease`：同一 Linux 主机的 SDK 控制路径用 `flock` 竞争 `/tmp/aubo_motion_writer.lock`，保证参与该机制的进程只有一个运动写入者。**它无法约束另一台电脑、示教器或不遵守锁协议的程序。**切换的关键是旧输出停止、旧命令失效、反馈重新对齐后才启用新控制。见 S4、S10。

##### A15｜两个不同 ROS 节点如何同步状态？

【实现＋原理】用 Topic 广播运行状态，用 Service 请求启停并确认请求是否被接受，用 Action 表达有进度、可取消的长任务。比如任务编排读取 `/sorting/state`，控制服务发起分拣，并观察后续状态完成闭环。

消息传输不等于原子事务；“服务返回成功”可能只代表受理，停止命令也不等于已停稳。应结合任务上下文、终态、新鲜度、超时和停止确认。对于只用字符串或 Bool 的接口，增加任务 ID／序号可以降低旧消息误触发风险，这是接口强化方向，不能当成全仓库已经实现的统一机制。

##### A16｜目标 ID 怎么管理，怎样避免重复抓取？

【实现】`InstanceQueue` 结合类别、空间距离和 footprint 等信息做跨帧关联，管理 `CANDIDATE → READY → RESERVED → DONE`，失败进入 `REVIEW`。多帧稳定后才可分配，执行前先预留；完成目标短暂保留以屏蔽残留画面。ID 在 `clear()` 后也不立即重用，但这不代表跨进程重启永久唯一。

缓存本身要求调用方串行访问；机械臂运动期间不持有目标队列锁。遮挡、同类目标靠近和较大移动仍可能导致关联歧义，需要复核机制，不能承诺绝不重复。见 S8。

##### A17｜目标丢失、抖动或位姿异常怎么办？

【实现】输入先做 TF 与有限值等校验，控制时检查目标年龄、反馈年龄和运动限制；实例缓存用多帧确认、位置平滑及预留目标扰动检测降低误抓。视觉状态机依据配置在跟踪、对齐、短时衰减续行、搜索恢复或保持之间切换，当前代码也包含受控停止与返回观察位相关状态。

**要按实际启动参数回答丢失策略。**不能把“所有丢失都立刻回零”当成实现，也不能无限沿最后速度运动。安全锁存或搜索超时进入保持，重新识别后还要确认是有效的新观测。见 S3、S8。

### 项目二：ROS 移动机器人自主导航与机械臂协同作业（P0）

#### 1. 串口通信

##### B01｜上位机与 STM32 使用什么协议？

【实现】上位机通过 `serial` 库收发自定义二进制协议，默认波特率 115200，帧头 `0x7B`、帧尾 `0x7D`。下发固定 11 字节，上报固定 24 字节，中间多字节数值按高字节在前解码，校验为逐字节异或 BCC。**不是 Modbus RTU，也不是 CRC16。**STM32 端的串口参数需对照固件补核验。见 S11、S12。

##### B02｜下发速度指令帧有哪些字段？

【实现】偏移从 0 计数：

|偏移|字节数|含义|
|---|---:|---|
|0|1|帧头 `0x7B`|
|1～2|2|预留，当前写 0|
|3～4|2|`linear.x × 1000`，有符号 16 位，高字节在前|
|5～6|2|`linear.y × 1000`，同上|
|7～8|2|`angular.z × 1000`，同上|
|9|1|对偏移 0～8 求 XOR|
|10|1|帧尾 `0x7D`|

线速度输入是 m/s，角速度输入是 rad/s。乘 1000 是定点缩放，不是都变成 mm/s。当前转换代码应进一步补有限值和范围检查，避免超范围浮点数转 `short`。【改进】

##### B03｜STM32 上传状态帧包含什么？

【实现】`[0]` 帧头；`[1]` 停止标志／预留字段；`[2～7]` 三个有符号速度量；`[8～13]` 三轴加速度原始值；`[14～19]` 三轴陀螺仪原始值；`[20～21]` 电池电压；`[22]` 对前 22 字节的 BCC；`[23]` 帧尾。速度和电压按 1000 比例换算，IMU 按头文件比例转换。

**上位机收到的是解算后的底盘速度，不是直接收到每个车轮的原始编码器计数。**不能根据“编码器里程计”就说帧中传了编码器脉冲。

##### B04｜一次只收到半帧怎么办？

【实现】当前 `Get_Sensor_Data_New()` 每次读 1 字节，用静态 `count` 和 24 字节数组跨调用累积，直到收满候选帧再判断帧尾与校验；读取不足 1 字节就返回未就绪，不发布新状态。它不是一次读取就必须拿到完整帧。

【边界】当前没有完整的半帧年龄超时和会话重置机制；只收帧头后长期停顿可能留下残帧。应将解析器状态对象化，并在半帧超时、重连时清理。

##### B05｜连续多个完整帧怎么拆分？

【实现】当前逐字节读取，每积满 24 字节验证一次，再继续读串口驱动缓冲区里剩下的字节，所以连续帧不会天然对应一次 `read()`。它没有一次批量读取后在用户态循环拆帧的环形缓冲设计。

【改进】批量读入接收缓冲，循环提取所有完整有效帧，保留尾部不足一帧的数据，可减少逐字节 API 调用开销。

##### B06｜校验错误后怎么重新找有效帧头？

【实现】本项目是 **BCC 错误**。当前收满候选 24 字节后把 `count` 归零，错误候选不发布，后续重新等帧头。它没有保存错误窗口并滑动一字节重新搜索，因此可能跳过候选帧内部的真实新帧头，恢复需要更多后续数据。

【改进】有界缓冲内遇候选错误只前进一字节，继续找 `0x7B`，并联合长度、帧尾、BCC 验证。不要把这种改进说成当前实现。

##### B07｜固定帧长为什么还要缓冲区？

【原理＋实现】固定的是协议消息长度，串口提供的是字节流，操作系统调度和读取时机不保证刚好一帧。缓冲区用于保留半帧、承接连续数据和支持重新同步。当前已有串口驱动缓冲及用户态的 24 字节组帧数组；“没有显式环形缓冲”不等于“完全没有缓冲”。

##### B08｜接收速度超过解析速度怎么办？

【原理】先按波特率与帧率算预算；115200、8N1 下理论约 11520 字节/s，24 字节帧的纯串口上限约 480 帧/s，实际更低。监控内核溢出、解析耗时和缓冲高水位，减少逐字节调用及热路径日志，必要时批量读或分离解析。

【改进】底盘状态可以在完成有效帧解析后合并发布最新状态；命令、事件和应答不能随意丢。容量只能吸收短时突发，长期速率失配必须降低流量或提高处理能力。

##### B09｜断线怎么检测、怎么重连？

【实现】读写异常走 `Handle_Serial_Failure()`，清本地速度、尝试发零速、关闭串口；端口未打开时主循环按间隔重试，默认 1 s。打开成功先发送零速，不恢复旧速度，并重置积分时间基准。

**实现缺口：**串口仍然 open 但对端不再上传有效帧时，`read()` 短读仅返回 false，没有完整的有效帧超时触发重连；解析器静态计数也未在重连处显式重置。应补 `last_valid_frame_time` 和会话清理。

##### B10｜上位机停止发有效速度时如何安全停车？

【实现】接收到 `/cmd_vel` 后记录时间，主循环超过默认 0.5 s 未收到新命令会发零速，超时状态避免持续重复触发；关闭和重连也尝试零速。

【边界】它用的是 ROS 时间，且超时检查受串口读取与主循环调度影响，因此不是严格 500 ms 截止保证；若进程崩溃或线缆断开，上位机无法保证零速送达。真正的失联制动还需 MCU 独立有效命令超时、驱动使能／制动策略，当前固件未核验。当前代码也没有完整验证输入速度的数值合法性。

#### 2. ROS 与导航

##### B11｜编码器和 IMU 如何转换成 ROS 消息？

【实现】STM32 上传底盘速度和 IMU 原始量；上位机将速度换算为 m/s、rad/s，按采样间隔积分平面里程计，并将机体系速度旋转到里程计坐标系。加速度除以 `ACCEl_RATIO`，角速度乘 `GYROSCOPE_RATIO`，通过姿态解算函数得到四元数，发布 `nav_msgs::Odometry` 和 `sensor_msgs::Imu`。

协方差、时间戳、轴方向和 `frame_id` 必须与传感器安装及融合配置一致。源码里 `odom.pose.pose.position.z` 被赋为内部航向变量 `Robot_Pos.Z`，对平面机器人是不合理的表达，应审查并改为正确高度；本文只记录问题，未改代码。见 S11、S12。

##### B12｜/odom、/imu、/cmd_vel 各有什么作用？

【实现＋原理】`/cmd_vel` 是期望机体速度输入，不是位置目标；`/odom` 提供局部运动估计及速度，会随积分漂移；`/imu` 提供角速度、线加速度及可用的姿态信息。三者方向不同：命令往下发，反馈往上报。还要检查消息 frame 与 TF，不要以为有 `/odom` 消息就必然有人发布同名 TF。

##### B13｜Gmapping、AMCL、move_base 分别负责什么？

【原理＋仓库配置】Gmapping 用二维激光和里程计进行 SLAM 建图；AMCL 在已知栅格地图中用粒子滤波定位；move_base 结合全局规划、局部规划与代价地图产生导航速度。AMCL 不负责建图，move_base 不直接驱动电机。仓库存在这些组件及 launch 配置，不能据此声称自己从零实现了这些算法。

##### B14｜map → odom → base_link 是什么关系？

【原理】`map` 是全局定位参考，允许定位校正造成跳变；`odom` 维护局部连续运动，会累计漂移；`base_link` 固连机器人。通常定位模块给出 `map → odom`，里程计或融合节点给出 `odom → base_*`，URDF 补齐机体和传感器关系。

【实现边界】本项目底盘默认帧名包含 `odom_combined` 和 `base_footprint`，不能机械背诵成所有配置都直接用 `odom → base_link`。必须查看实际 launch、融合节点和 TF 发布者，避免一个 child 有两个父变换。

##### B15｜怎么判断到达导航目标？

【实现】`BaseExecutor::navigateOnce()` 等待 move_base Action 终态，`SUCCEEDED` 才作为导航成功，同时处理停止、互锁和超时。复合作业还会验证停靠位姿、相机视野与机械臂工作条件，Action 成功不等于已经满足抓取要求。

【验证】记录目标与反馈位姿在同一坐标系的误差、TF 年龄，以及停止后的速度；业务到站验收应有单独标准。见 S13、S14。

##### B16｜Action 和 Service 区别？为什么导航用 Action？

【原理＋实现】Service 适合短请求／响应，没有标准的持续进度和取消生命周期；Action 提供目标、反馈、结果及取消，适合持续数秒到数分钟的导航。本项目用 Action 客户端管理 move_base，用 Service 做启动、停止或清理代价地图等请求。取消只是请求，必须观察终态或进一步确认停止，不能发送 cancel 后立刻认定底盘安全停稳。

##### B17｜导航失败如何重试？怎样避免多个任务控底盘？

【实现】`navigate()` 按配置执行有限次数尝试，失败后在符合条件时调用清理代价地图服务，再重试；超时、停止或服务异常会结束流程，不是无条件无限循环。任务生命周期锁和 busy／stop 等状态限制任务准入，切换到近场速度控制前取消导航并发送停止。

【边界】这保证的是本任务编排内部的所有权；其他节点仍可能发速度。整机层面还需检查 velocity mux、话题路由及外部发布者，不能声称 Action 自带全系统底盘互斥。见 S13、S14。

##### B18｜怎样实现不超过 0.1 m 的停靠？

【实现】先导航到预停点，再进行允许条件下的低速近场直行和航向修正，利用 TF 反馈闭环评估位置、横向和角度误差，并限制距离、超时与无进展时间。`scenario.yaml` 当前近场位置容差为 0.06 m，最终航向容差为 0.025 rad，配置可覆盖。

**0.06 m 是内部判定阈值，不是已经证明真实误差小于 0.1 m。**定位偏差、轮滑、延迟和机械安装都会影响真实误差；需要独立测量多次停靠的误差分布，记录负载、初始姿态、地面和成功条件。若定位精度不够，应引入工位视觉或标志物辅助，这是进一步方案。见 S13、S15。

### 项目三：STM32 底层电机控制（P1）

> [!warning] 本节统一为【原理／待核验】
> 未发现 MCU 固件，以下可以用于解释设计，但不能说成已核对的个人实现。需补 STM32 工程、芯片型号、时钟树、定时器与 DMA 配置、控制代码和逻辑分析仪记录。

##### C01｜UART 普通中断接收与 DMA 接收区别？

普通 RXNE 中断通常每个字节都需 CPU 服务，逻辑直观但高吞吐时中断开销大。DMA 根据 UART 接收请求自动搬运数据到内存，CPU 在半满、全满或 IDLE 等事件时集中处理；它降低搬运开销，不负责协议解析，也不会自动解决溢出。

##### C02｜DMA 如何搬运 UART 数据？

配置对应 UART RX 的 DMA 通道／数据流、外设寄存器地址、内存地址、方向、宽度、计数和地址自增。收到 UART DMA 请求时，DMA 将接收寄存器数据写入缓冲区并更新剩余计数。UART 寄存器地址固定、内存地址递增；具体映射和合法存储区域要查 F407 手册，不能任意指定。

##### C03｜DMA + IDLE 接收流程？

启动 DMA 接收并启用 UART IDLE 中断；产生空闲事件后按芯片规定清标志，通过剩余计数推导写入位置，计算自上次消费以来的新数据段，交给解析任务。循环 DMA 还需半满／全满事件支持持续无空闲的数据流。中断内尽量只记录位置、置位或通知，不做长耗时解析；IDLE 不是业务帧结束保证。

##### C04｜DMA 环形写入快于读取怎么办？

维护生产与消费进度，及时消费连续区与回绕区，记录圈数或溢出事件，防止仅比较模 N 下标漏掉整圈覆盖。检测覆盖后标记数据丢失、重新同步协议，必要时安全停车；根因是处理能力或流量失配。若读指针更新依赖中断，需保证最坏服务延迟小于可覆盖窗口，不能只靠扩大数组。

##### C05｜1 ms 定时器中断怎么配置？

更新频率公式为 `f_update = f_TIM / ((PSC+1)(ARR+1))`。例如**假设**实际定时器输入为 84 MHz，可取 `PSC=83、ARR=999` 得 1 kHz。F407 某些 APB 分频配置会让定时器时钟是 APB 时钟的两倍，必须从时钟树确认；这个例子不能当成你的真实寄存器配置。还要设置更新事件、中断和 NVIC 优先级。

##### C06｜为什么 PID 放定时器中断？

固定采样间隔使差分、积分和参数有确定意义，控制响应也更可预测；中断中读取速度、计算控制量并更新 PWM，可避免主循环业务延迟。不过这是架构选择，也可用定时器触发高优先级控制任务。串口打印、阻塞 I²C、动态分配和长循环不应挤进高频控制路径。

##### C07｜中断执行超过 1 ms 会怎样？

控制截止时间被错过，低优先级工作受饿、采样和输出产生抖动；普通中断标志不是无限事件队列，多个更新可能合并，不能认为所有漏掉的周期都会排队补执行。用 GPIO 翻转配逻辑分析仪或 DWT 周期计数测最坏执行时间，减少中断工作并保留余量。

##### C08｜增量式与位置式 PID 区别？

位置式直接计算控制输出：`u[k]=Kp·e[k]+Ki·Ts·Σe+Kd·(e[k]-e[k-1])/Ts`。增量式计算 `Δu[k]`，再累加得到输出，常见形式是 `Kp(e[k]-e[k-1])+Ki·Ts·e[k]+Kd/Ts·(e[k]-2e[k-1]+e[k-2])`。

两者都需限幅和抗积分饱和，系数是否已经吸收 `Ts` 要看代码。增量式不是天然不会积分饱和，也不能只存一个误差就算完整 PID。

##### C09｜前馈与 PID 怎样配合？

前馈按目标和模型预先提供主要驱动力，PID 修正模型误差和外部扰动。例如 `u=u_ff(v_ref,a_ref)+u_PID(v_ref-v_meas)`，其中前馈可含速度项、加速度项及经过标定的摩擦补偿。最终统一限幅，并处理饱和时的积分；需要辨识数据与对照实验，不能把任意常数偏置称为已经完成模型前馈。

##### C10｜编码器怎样计算转速？

在 `Ts` 内读取有符号计数差 `ΔC`，输出轴转速 `rpm=60·ΔC/(C_per_rev·Ts)`。`C_per_rev` 必须说明是电机轴还是输出轴、是否包含 AB 四倍频和减速比。处理计数器回绕和方向，低速计数分辨率不足时可采用测周期或融合方法；滤波会增加反馈延迟。

##### C11｜异常时清目标速度还是关闭 PWM？

取决于故障和机械风险。普通命令超时可进入受控减速，目标降零并处理积分；过流、驱动故障或急停可能需要按硬件方案撤销使能或安全制动。**清目标不代表零输出，关闭 PWM 也不必然代表制动**，可能变成滑行。带重力负载的关节尤其要结合抱闸与驱动安全机制，具体动作以真实硬件设计为准。

##### C12｜看门狗与通信超时有什么区别？

看门狗处理程序未按预期运行的情况，超时触发复位等恢复；通信超时处理上位机失联或命令失效，程序可以仍正常运行。两者应独立存在：通信超时进入安全状态，系统任务健康后才喂狗。若在固定中断里无条件喂狗，即使业务死锁也可能永远不复位。

### 项目四：视觉识别、运动规划及 AGV 作业（P2）

##### D01｜YOLO-OBB 与普通检测区别？

【原理＋实现边界】普通检测框一般是轴对齐矩形，OBB 预测旋转矩形的中心、尺寸和方向，更适合倾斜物体和抓取方向估计。OBB 角度有范围、长短边交换和对称性约定，不能直接把图像角度当机器人 yaw；它也不直接提供完整 6D 位姿。本仓库有 YOLO／RGB-D 适配实现，但网络改进内容、训练指标与个人贡献仍需训练工程和实验记录证明。见 S9。

##### D02｜RGB-D 如何得到三维坐标？

【原理＋实现】对齐彩色与深度后，以像素 `(u,v)` 和深度 `Z` 反投影：`X=(u-cx)Z/fx，Y=(v-cy)Z/fy`。先处理相机畸变、深度单位、无效值和背景混入，再以图像时刻 TF 转到机器人坐标系。

项目不同配置有深度定位、平面／几何高度约束等策略，移动颜色检测还会筛选预期顶面附近的深度点；不能概括成“总是取检测框中心的一个深度值”。部分配置发布 Z 是物体中心高度，也不是原始可见表面高度。见 S9。

##### D03｜手眼标定作用与坐标变换？

【原理＋实现】它确定相机与机器人之间的刚性外参，让视觉坐标可以用于机械臂控制。眼在手外时 `p_B = T_BC·p_C`；眼在手上时 `p_B=T_BE(q)·T_EC·p_C`。约定 `T_AB` 将 B 系坐标变到 A 系，使用齐次坐标，不能把矩阵顺序写反。

手眼求解常可写成 `AX=XB`，但 A、B 的定义取决于安装模式与相对运动约定。仓库通过 TF／标定发布脚本接入外参；要补标定样本、重投影或位姿残差及独立验证，不能只凭“TF 能查到”就证明标定准确。

##### D04｜DH 参数怎样描述机械臂？

【原理】标准 DH 用 `a、α、d、θ` 描述相邻坐标系关系，常写为 `Rz(θ)·Tz(d)·Tx(a)·Rx(α)`，转动关节变量通常是 θ。要说明采用标准还是改进 DH，它们的建系和变换顺序不同。当前控制代码从 URDF 建 KDL 链，不能把用于理论推导的 DH 表直接说成运行时唯一模型来源。

##### D05｜正运动学与逆运动学区别？

【原理＋实现】正运动学由关节角算末端位姿；逆运动学由期望位姿求关节解，可能多解、无解或接近奇异。抓取规划要结合关节限位、碰撞、可达性与连续性选择解。视觉伺服通过雅可比求关节速度属于微分运动学，不等于每周期都重新求完整位置逆解。

##### D06｜六轴机械臂如何规划轨迹？

【实现＋原理】先依据目标与场景求可行关节路径，检查碰撞、限位和约束，再做时间参数化以满足速度、加速度等限制，最后由控制器或执行后端采样输出。几何路径与带时间轨迹是两层概念。项目使用 MoveIt，具体算法以启动参数为准；不能把使用 RRTConnect 和自行改进规划算法混成同一贡献。执行阶段还要检查实际跟踪和反馈新鲜度。

##### D07｜视觉检测误差与抓取误差怎样评估？

【原理／待补实验】分别评价检测的 precision／recall／OBB mAP、定位的三维位置和方向误差，以及端到端抓取成功率。位置可报告 MAE、RMSE、P95／最大值，方向要考虑物体对称性；实验需给真值、样本数、距离、物体类别和成功判据。

“内部误差达到 1 mm 阈值”不等于“独立测得真实抓取精度 1 mm”；网络推理时间也不等于采图到执行的端到端延迟。现有代码不能独立证明简历中的精度与成功率。

##### D08｜AGV 搬运怎样保证移动和夹爪动作顺序？

【实现】任务状态机依次处理机械臂运输姿态、导航、停靠验收、观察位和分拣；分拣内部按规划运动、接近、夹持、搬运、释放推进，依据结果进入下一步，失败转错误／恢复流程。停止时同时取消导航、分拣和相关执行，并区分 `STOPPED` 与 `STOP_UNCONFIRMED`。

不要只用几个固定 `sleep()` 假装动作完成；仿真的附着确认也不能当成真实夹爪力传感反馈。未确认停止时不准接新任务，是比“发过停止命令”更强的业务条件。见 S7、S14。

## 三、C++ 基础与多线程高频面试题

### 1. C++ 语言基础

##### E01｜左值与右值有什么区别？

【原理】先区分表达式值类别：glvalue 强调对象身份，rvalue 包含 prvalue 与 xvalue；lvalue 属于 glvalue。口述可说左值通常能指认已有对象，右值常用于临时结果或可转移资源的表达式，但不能仅用“能否取地址”定义。**有名字的 `T&&` 变量表达式仍是左值**，字面量也不全是右值，例如字符串字面量是左值数组。

##### E02｜std::move() 做了什么？

【原理】它把表达式转为相应的右值引用形式，本身不搬资源；真正的转移取决于后续是否选择移动构造／移动赋值。移动后对象通常有效但状态未指定，应按类型契约使用。对 const 对象 move 往往仍调用拷贝，因为普通移动构造通常不能接受 `const T&&`。

##### E03｜移动构造与拷贝构造区别？

拷贝按类型语义复制状态，拥有独占资源时常需要深拷贝；移动通常接管资源并让源对象保持可析构状态，适合线程句柄、独占指针、大容器等。不是所有类型的拷贝都深拷贝，也不是所有移动都 O(1)。移动可能抛异常时，`vector` 扩容可能选择拷贝以维护异常保证。

##### E04｜T&、const T&、T&& 区别？

`T&` 通常绑定可修改左值；`const T&` 可绑定左值和临时对象但不能经该引用修改；非模板场景的 `T&&` 通常绑定右值，便于移动。模板推导中的某些 `T&&` 是转发引用，应结合引用折叠与 `std::forward`。临时对象经特定引用初始化可延长生命周期，但返回局部对象引用、把参数引用存起来都可能悬空。

##### E05｜什么是 RAII？

把资源获取与释放绑定到对象生命周期：构造后建立资源所有权，析构释放，异常路径也自动清理。`unique_ptr`、`lock_guard`、文件句柄封装都是例子。项目 `MotionLease` 析构释放文件锁也体现 RAII；线程则需在资源销毁前协作停止并 join，单纯把 `std::thread` 放成员里不自动解决退出。

##### E06｜unique_ptr 与 shared_ptr 区别？

`unique_ptr` 表示独占所有权，可移动不可拷贝；`shared_ptr` 通过控制块共享所有权，有引用计数成本，可配 `weak_ptr` 打破环。线程安全的是特定的控制块共享操作，不代表被管理对象线程安全，也不代表可以无同步并发修改同一个普通 `shared_ptr` 实例。回调捕获对象时还需防止循环引用和对象提前销毁。

##### E07｜虚函数与虚函数表是什么？

虚函数允许经基类指针／引用调用时按对象动态类型分派，实现运行时多态；虚表和虚指针是常见 ABI 实现方式，标准不强制具体布局。项目硬件接口继承 `RobotHW` 并 override 对应方法是应用例子。构造／析构期间的虚调用有特殊分派规则，不能依赖它调用尚未构造或已销毁的派生部分。

##### E08｜基类析构函数为什么通常要 virtual？

若需要经基类指针删除派生对象，虚析构保证正确执行派生析构，避免未定义行为。不是所有基类都必须公开虚析构；不允许多态删除的接口也可采用受保护非虚析构。面试重点是**使用场景与所有权**，不是“只要继承就一定加 virtual”。

##### E09｜vector、deque、list 区别？

|容器|布局与访问|典型插删与取舍|
|---|---|---|
|vector|连续内存，随机访问 O(1)|尾插摊还 O(1)，中间插删 O(n)；扩容会失效迭代器和引用|
|deque|分段存储，随机访问 O(1)|两端插删 O(1)，中间 O(n)；迭代器失效规则需按操作区分|
|list|节点链表，不支持 O(1) 随机访问|已知位置插删 O(1)，定位仍 O(n)；分配与缓存局部性成本较高|

项目视觉队列使用 deque 便于头部消费和尾部插入；“list 插入快”不能脱离查找和分配成本讨论。

##### E10｜static、const、constexpr 区别？

`static` 含义与位置有关：局部静态存储期、类静态成员或文件作用域内部链接等；`const` 约束经该对象或访问路径的修改，不必然是编译期常量；`constexpr` 允许常量求值并对声明施加相应要求，constexpr 函数仍可运行期调用。C++11 保证局部静态对象初始化线程安全，不保证其后续所有成员操作线程安全。

### 2. 多线程与同步（P0）

##### F01｜std::thread 创建后有哪些状态，如何安全退出？

区分线程实际执行的运行／阻塞／结束与句柄的 joinable／非 joinable。线程函数已返回但尚未 join，句柄仍可能 joinable。退出采用停止标志、唤醒等待、取消或限时结束外部工作、最后 join；`std::thread` 没有通用安全的强制 kill。C++20 `jthread` 提供协作停止与析构 join，但仍不能自动打断不可取消 I/O。

##### F02｜join 与 detach 区别？

`join()` 等待线程结束并回收关联；`detach()` 解除线程对象与执行线程的关联，之后不能再通过它等待。长期捕获 `this` 的机器人工作线程通常应 join，detach 容易让线程访问已析构对象。析构一个仍 joinable 的 `std::thread` 会调用 `std::terminate()`。

##### F03｜主线程退出后其他线程会怎样？

若 `main` 返回导致进程退出，其他线程也随进程终止，不能指望其正常清理；若到达某个局部 `std::thread` 析构且仍 joinable，还可能先触发 terminate。主线程只退出一个函数、线程对象仍在其他作用域时，情况又不同。正确方案是进程退出前显式停止并回收，而不是依赖操作系统收尾。

##### F04｜mutex、atomic、condition_variable、信号量区别？

mutex 保护复合共享不变量；atomic 提供某个对象的原子操作及可选内存顺序；条件变量让线程等待由锁保护的谓词；信号量维护许可计数，适合资源数和任务通知。队列内容、索引和退出条件往往构成整体协议，不能把一个 bool 换成 atomic 就宣布整个队列线程安全。

##### F05｜lock_guard 与 unique_lock 区别？

`lock_guard` 构造上锁、析构解锁，简单且不支持中途释放；`unique_lock` 可延迟加锁、解锁、重新上锁和移动所有权，适合条件变量等待。多个锁可用 `std::lock` 配合 RAII 或 C++17 `scoped_lock` 避免手工顺序错误，但仍需审查跨调用的锁顺序。

##### F06｜condition_variable::wait 为什么传锁？

它必须把“释放 mutex 并进入等待”作为协调好的操作完成，醒来后重新持锁，才能在同一互斥协议内检查条件，避免检查与睡眠之间丢通知。常写 `cv.wait(lock, [&]{ return stop || !queue.empty(); });`；生产端在同一 mutex 下修改谓词，再通知。条件变量自己不存储“有任务”这个事实。

##### F07｜为什么考虑虚假唤醒？

wait 可能在没有满足业务条件时返回；即使确有通知，资源也可能已被其他线程取走。因此必须循环检查谓词，使用带 predicate 的 wait 最直观。不能 `if(empty) wait()` 后就无条件 pop，停止标志也要放在谓词里，防止关闭时线程永久等待。

##### F08｜notify_one 与 notify_all 怎么选？

新增一个普通任务且任意一个消费者都能处理时，通常 notify_one；关闭队列、多个等待条件可能满足或所有线程都应观察状态变化时用 notify_all。不同谓词共用一个条件变量时要防止唤醒“错误的等待者”导致进展问题，可拆条件变量或使用广播。通知不是把锁转交给指定线程，也没有一般性的公平保证。

##### F09｜死锁怎么产生，怎么避免？

常见场景是线程一持 A 等 B，线程二持 B 等 A；也包括持锁调用外部代码后被回调重入。统一锁顺序、缩小临界区、避免持锁 SDK／服务调用、必要时多锁统一获取。join 时不能持有被退出线程需要的锁，否则会形成“等线程退出”和“等锁”的相互等待。

##### F10｜数据竞争和线程安全是什么？

两个线程并发冲突访问同一内存，其中至少一个写，且不是受正确同步约束的原子访问，就可能产生 data race，在 C++ 中导致未定义行为。线程安全是接口在约定并发使用方式下仍维持正确性。没有 data race 仍可能存在逻辑竞态，例如“检查空”和“取出”分开锁定，或读取到跨时刻的六轴快照。

### 3. 无锁编程（P0）

##### G01｜什么是无锁？是否意味着没有同步？

lock-free 是进展性质：即使某个线程停顿，系统整体仍保证有操作取得进展；不等于每个线程都有有界完成时间，后者接近 wait-free 的要求。无锁仍依靠原子操作和内存顺序同步，也不等于没有 CPU 原子指令代价。malloc、日志、SDK 调用可使“用了无锁队列的系统”整体仍会阻塞。

##### G02｜atomic 与普通变量区别？

atomic 对该对象提供原子读写／读改写，可建立线程同步；普通变量的并发冲突访问需 mutex 等同步。atomic 不自动维护多个变量之间的业务不变量，也不自动保证 `load()+store()` 组成的增量操作原子，应使用 `fetch_add` 或正确 CAS。具体类型是否无锁可查询 `is_lock_free()`。

##### G03｜relaxed、acquire、release 有什么作用？

relaxed 只提供该原子对象的原子性与修改顺序，不发布其他数据；生产者完成数据写入后 release 发布索引，消费者 acquire 读到对应发布值时，建立数据可见关系。自身独占更新的索引读取通常可 relaxed，读取对端进度需要相应同步。定义依据见 [C++ 标准草案：原子内存顺序](https://eel.is/c++draft/atomics.order)。

##### G04｜SPSC 环形队列为什么可以不用 CAS？

因为写索引只有生产者修改，读索引只有消费者修改，不存在同一索引的多写者竞争；各自读取对端索引判断满空，用 release／acquire 交接槽位。成立前提是严格的一生产者、一消费者，不能让“丢旧点”的生产者顺手修改消费者读索引而破坏协议。

##### G05｜为什么用一个空槽区分满空？

采用模 N 下标时，空条件 `read==write`；若再允许写满 N 个槽位，满时也可能相等。预留一个槽后，满为 `(write+1)%N==read`，可用容量 N−1。也可以用单调计数或额外标志设计，但同步与溢出推理更复杂，不能把“必须浪费一个槽”当成所有环形队列的定律。

##### G06｜怎样保证消费者读到完整数据？

生产者先写槽位的全部字段，再 release 发布写索引；消费者 acquire 观察到新写索引后才读槽位；读完后 release 发布读索引，生产者 acquire 观察空位后才复用槽位。不是把 payload 每个字段都设成 atomic，而是用槽位所有权和同步关系保证普通字段没有并发冲突。

##### G07｜head、tail 如何同步？

先约定名字，例如 head 为下一写位置、tail 为下一读位置；生产者写 head、消费者写 tail。生产者 acquire 读 tail 检查可复用空间，消费者 acquire 读 head 检查可读数据，各自 release 发布进度。不同资料命名可能相反，面试先画数据流，避免只背 head／tail 术语。必要时将两个热点索引分开缓存行减少伪共享。

##### G08｜多生产者为什么更难？

多个线程竞争同一写端，不但要原子预留槽位，还要区分“已预留”和“数据已完成”；某个生产者预留后停顿，消费者不能读取半成品。还需处理顺序、回绕、容量与内存回收，常用 CAS／序号等协议。把 SPSC 的写索引改为 `fetch_add` 并不能得到正确的 MPSC／MPMC。

##### G09｜CAS 与 ABA 是什么？

CAS 比较当前值与期望值，相同才更新；失败会反馈当前观察值，weak 允许伪失败，常放循环。ABA 是某地址值从 A 变 B 又变回 A，CAS 以为没变但对象或状态已经更换。指针无锁结构可采用版本标签、hazard pointers 或 epoch 管理，具体方案还要处理回收与版本回绕；本项目 SPSC 主链不应硬套链表 ABA 叙述。

##### G10｜无锁一定比 mutex 队列快吗？

不一定。原子指令、缓存行争用、CAS 重试与忙等都有成本，低竞争下短 mutex 临界区可能足够快，阻塞队列还能减少空闲 CPU。比较时应看吞吐、P99 延迟、CPU 占用、生产消费比例和容量，并把 SDK 通信成本算进去。项目选 SPSC 是因为拓扑匹配、能避免控制生产端等待互斥，而不是证明所有无锁方案都更快。

## 四、串口通信与网络协议面试题

### 1. UART、DMA 与通信接口

##### H01｜UART 基本通信过程？

双方预先约定波特率与帧格式，TX 将并行数据序列化为起始位、数据位、可选校验位和停止位，RX 按约定采样恢复字节。UART 不传独立时钟，双方波特率误差与线路质量会影响接收；硬件字节帧不等于应用层消息帧。

##### H02｜8N1 代表什么？

8 个数据位、无奇偶校验、1 个停止位，加上 1 个起始位，每字节通常占 10 个 bit 时间。115200 波特下约 86.8 μs/字节，理论有效载荷约 11520 字节/s。这里的 N 是 UART 硬件无奇偶校验，不排斥应用协议另加 BCC 或 CRC。

##### H03｜UART 和 RS232 区别？

UART 是串并转换与异步字符收发机制，RS232 规定电气与接口特性，二者层次不同。MCU 的逻辑电平 UART 不能直接接 RS232 电压，需电平转换器；RS232 常用于点对点，逻辑极性与电压也不能按 TTL 直接理解。

##### H04｜RS485 与 CAN 都差分，有什么区别？

RS485 主要定义差分电气接口，寻址、帧格式、仲裁需上层协议解决，常见半双工多点连接；CAN 还定义链路层的帧、位仲裁、确认、错误检测和故障限制机制。差分只说明抗共模干扰的传输方式，不能推导二者协议兼容。速率与距离都取决于布线、收发器和标准模式。

##### H05｜CAN 怎样仲裁？

节点发送时同时监测总线，显性位覆盖隐性位；在仲裁字段发送隐性却读到显性，就退出本次竞争并等待。标准数据帧中数值较小的标识符通常优先，但还需考虑标准／扩展帧等仲裁字段，不能只比较任意两个完整 ID 数字。仲裁不破坏获胜帧，与普通“碰撞后重发”有区别。

##### H06｜UART 中断与 DMA 区别？

对应 [[#C01｜UART 普通中断接收与 DMA 接收区别？]]：逐字节中断由 CPU 搬数据，DMA 批量自动搬运；两者都需要处理 UART 错误、缓冲边界与协议解析。面试落到项目时应补真实 DMA stream／channel、缓冲长度和实际中断频率，当前仓库不能证明这些参数。

##### H07｜DMA 怎样配合 IDLE 接收不定长数据？

用 IDLE 作为“现在可以收割新增数据”的事件，通过 DMA 剩余计数确定区间，再交给有状态解析器。空闲可能出现在一帧内部，也可能长时间没有空闲，所以配合半满／全满及协议长度验证。流程见 [[#C03｜DMA + IDLE 接收流程？]]；不要把“一次 IDLE”直接解释为“一条完整业务消息”。

##### H08｜为什么考虑循环覆盖？

DMA 不会因为 CPU 没读而自动停在安全位置，循环模式会覆盖旧数据。必须有消费进度、可观测的溢出策略与最坏延迟预算；只依赖一次 IDLE 中断在持续数据流中可能来不及。发生覆盖后旧数据可信性失效，要丢弃受损窗口并重新同步，不可继续当作完整状态。

### 2. 帧解析与异常处理（P0）

##### I01｜TCP 与 UART 为什么出现应用层粘包、半包？

两者给应用提供连续字节序列，应用每次 read 的长度与业务消息边界没有一一对应关系。可能读到一条消息的一部分，也可能多条一起读到；TCP 的合并、分段与调度，UART 的字节到达和驱动缓冲都影响读取分块。TCP 是可靠字节流，UART 本身没有相同的可靠重传保证，二者不能混为一谈。

##### I02｜固定长度协议如何确定完整？

先找候选帧头，累计至少规定长度，再校验固定偏移帧尾与校验值，并做字段范围验证；数据不够时保留等待。项目上报长度为 24 字节，验证偏移 23 的帧尾和偏移 22 的 BCC，不能只看到 `0x7D` 就提前结束。仅长度满足也不保证帧有效。

##### I03｜错误帧全丢还是滑动一字节？

对于有噪声的流式自定义协议，候选失败后滑动一字节重找通常更利于恢复，避免把内部真正的帧头一起扔掉；但要限制扫描量与缓冲容量。项目当前是整段候选结束后重新等帧头，滑动搜索属于待改进项。若已明确串口会话重建，可丢弃整段会话残留并重新初始化，两种情况要区分。

##### I04｜数据里出现与帧头相同的字节怎么办？

固定长度协议中，在已锁定候选帧期间把它当数据，不立即重新起帧，再用长度、尾和校验共同验证。候选失败时再滑动搜索；若要设计新变长协议，可用长度字段与转义／编码机制。BCC 有碰撞概率，因此所有校验通过也不是绝对没有误判。

##### I05｜只有帧头，后续一直不来怎么办？

记录半帧起始或最后字节时间，超过依据波特率与调度余量设置的超时后清理残帧并重新找头。超时不能直接套一个字节时间，USB 串口和操作系统调度会带来批量延迟。项目当前未完成半帧超时，这是改进点；超时判定宜使用单调时钟，避免系统时间调整影响。

##### I06｜CRC16 怎么计算，怎样检测错误？

CRC16 是一类 16 位多项式校验，必须先约定多项式、初值、输入输出反射、最终异或与字节顺序，不能只说“CRC16”。例如 Modbus RTU：初值 `0xFFFF`，常见右移实现用反射多项式 `0xA001`，逐字节异或并做 8 次移位／条件异或，线上低字节先发。接收端按同样规则比较，不能纠错，也不能保证发现所有可能错误。[Modbus 串行规范，附录 B](https://www.modbus.org/file/secure/modbusoverserial.pdf)

项目 `Check_Sum()` 只是 XOR，即 BCC，不包含上述 CRC 运算。若升级校验，收发双方必须一起改协议。

##### I07｜为什么保存最后有效帧时间戳？

它表示“最后一次获得可信新状态”，用于区分端口打开、收到噪声和有效设备反馈。无效校验、重复缓存发布不能刷新它，否则失联会被掩盖。项目已有最后 `/cmd_vel` 时间，但底盘驱动尚缺完整的最后有效状态帧超时机制；机械臂反馈路径则有新鲜度检查，两个模块不要混讲。

##### I08｜接收缓冲满时丢新还是丢旧？

按语义选：遥测倾向保持最新有效状态，但要保留重新同步能力；事务应答和有顺序的命令不能随意覆盖，应报错、背压或中止。丢字节可能破坏消息，必须明确解析器如何恢复并记录 overflow 计数。不能对所有队列统一套“丢旧”，尤其带时间约束的机械臂轨迹不能随意丢点。

##### I09｜上位机接收、发送、解析一定三个线程吗？

不一定，可用一个事件循环、接收兼解析加独立发送、或更细分架构，取决于阻塞、负载和响应要求。本底盘当前是主循环逐字节接收解析并 `spinOnce()`，速度回调内直接写串口，没有三线程流水线。机械臂发点独立线程是另一种负载下的选择。拆线程增加同步和退出复杂度，应有测量依据。

##### I10｜怎样区分 UART、DMA、协议层异常？

分层取证：UART 看波特率、接线、噪声、ORE／FE／PE 等；DMA 看请求映射、计数、回绕、半满／全满及错误标志；协议看原始字节、长度、头尾、校验、重同步与时间戳；系统看调度、缓冲水位和断线状态。用逻辑分析仪与时间标记关联现象，避免只看“无数据”就认定是 CRC 或串口损坏。

### 3. Modbus 与 TCP

> 本组是协议原理扩展，不表示机器人项目用了 Modbus。Modbus 说明以官方规范为依据，TCP 以 RFC 9293 为依据。

##### J01｜Modbus 与 UART、RS485、TCP 什么关系？

Modbus 定义应用层数据模型和功能操作。RTU 是串行承载形式，可结合 UART 字符收发与 RS485 等电气接口；Modbus TCP 在 TCP 上承载。同一串口能运行自定义协议，也能运行 Modbus，使用 RS485 不自动等于用了 Modbus。[Modbus 官方规范入口](https://www.modbus.org/modbus-specifications)

##### J02｜Modbus RTU 帧格式？

地址、功能码、数据、CRC16，以静默时间界定边界；数据长度与功能码有关。没有本项目固定的 `0x7B`／`0x7D` 帧头尾；正常响应和异常响应格式不同，异常响应功能码置最高位并附异常码。[Modbus 串行规范](https://www.modbus.org/file/secure/modbusoverserial.pdf)

##### J03｜为什么要 3.5 字符时间静默？

它用时间间隔区分连续 RTU 帧，不依赖专用起止字节。低波特率下依据字符时间判断，高于 19200 bit/s 时规范建议采用固定的 750 μs 帧内超时和 1.750 ms 帧间延时；计算字符时间必须依据实际字符格式，不能直接套 8N1。[Modbus 串行规范 §2.5.1](https://www.modbus.org/file/secure/modbusoverserial.pdf)

##### J04｜03、04、06、10 功能码是什么？

均按十六进制：`0x03` 读保持寄存器，`0x04` 读输入寄存器，`0x06` 写单个保持寄存器，`0x10` 写多个保持寄存器。要区分协议数据地址与手册中 4xxxx 等展示地址的偏移，并核对多寄存器浮点数的字序。[Modbus 官方应用协议规范入口](https://www.modbus.org/modbus-specifications)

##### J05｜RTU 与 Modbus TCP 区别？

RTU 使用串行地址、PDU、CRC 和时间边界；TCP 形式使用 MBAP 头（事务标识、协议标识、长度、单元标识）加 PDU，不再携带 RTU CRC。TCP 客户端要按 MBAP 长度收齐消息并匹配事务，不能一次 recv 就当完整响应。MBAP 长度包含单元标识及后续 PDU。[Modbus 官方 TCP／应用规范入口](https://www.modbus.org/modbus-specifications)

##### J06｜TCP 握手为什么三次？

双方需要交换并确认各自初始序号，完成双向连接状态同步：SYN、SYN+ACK、ACK。第三次确认使服务器知道自己的 SYN 已被对端接收，并有助于处理旧连接中的延迟报文。它不是业务身份认证，也不保证应用已经开始处理请求。[RFC 9293 §3.5](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5)

##### J07｜SEQ、ACK Number 表示什么？

SEQ 标识报文中数据在字节流里的序号，ACK 通常表示期望收到的下一个序号，是累计确认。SYN 和 FIN 各消耗一个序号；纯 ACK 不消耗数据序号。不能把 ACK 当作“收到第几个包”。[RFC 9293 §3.1、§3.4](https://www.rfc-editor.org/rfc/rfc9293.html)

##### J08｜TCP 如何可靠有序交付？

通过序号、确认、重传、校验、重复数据处理与接收重排等维持字节流可靠有序，滑动窗口和拥塞控制约束发送。连接故障最终仍可能返回错误，也不能把 TCP ACK 当成对端业务已执行，更不提供严格实时截止时间。[RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)

##### J09｜TCP 为什么还要应用层处理边界？

TCP 只保留字节顺序，不保留应用一次 send 对应一次 recv 的边界。应用应定义固定长度、长度头或可消歧的分隔符，循环收齐后再解释消息；发送端也应按 API 语义处理部分发送。机器人控制协议通常还需序号、命令有效期和应答语义，以避免通信成功但业务状态不明。[RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)

## 五、两道队列手写题的回答提纲

### 1. mutex + condition_variable 有界阻塞队列

先问清：单／多生产消费、容量、满时是否等待、关闭后是否排空。建议契约：`push` 遇满等待，关闭后拒绝；`pop` 遇空等待，关闭后取完剩余再返回结束。

```cpp
// 示意协议，不是项目中已有代码。
// 以下每个方法中 q、closed 都由同一个 mutex 保护。
// capacity 在构造时必须 > 0。
push(value):
  unique_lock lock(mutex)
  not_full.wait(lock, closed || q.size() < capacity)
  if closed: return false
  q.push_back(value)
  lock.unlock()
  not_empty.notify_one()
  return true

pop(out):
  unique_lock lock(mutex)
  not_empty.wait(lock, closed || !q.empty())
  if q.empty(): return false   // 此时关闭且已排空
  out = move(q.front())
  q.pop_front()
  lock.unlock()
  not_full.notify_one()
  return true

close():
  { lock_guard lock(mutex); closed = true; }
  not_empty.notify_all()
  not_full.notify_all()
```

必须讲清：wait 的谓词、两个等待条件、关闭唤醒、最后 join；析构容器前所有访问线程已经停止。实际 C++ 实现还需定义元素拷贝／移动抛异常时的行为，不能只把伪代码机械翻译。

### 2. SPSC 有界环形队列

先声明：严格单生产者单消费者、N 个槽可用 N−1、满时返回失败、不支持并发 clear／覆盖旧点；示意中的元素读写应满足不抛异常等约束。

```cpp
// head: 下一写位置，仅生产者修改；tail: 下一读位置，仅消费者修改。
// data 槽位是普通对象，所有权通过索引交接。
try_push(value):
  h = head.load(relaxed)
  next = (h + 1) % N
  if next == tail.load(acquire): return false
  data[h] = value
  head.store(next, release)
  return true

try_pop(out):
  t = tail.load(relaxed)
  if t == head.load(acquire): return false
  out = data[t]
  tail.store((t + 1) % N, release)
  return true
```

这个简化模型用于解释原理，**不等于 `ReaderWriterQueue` 的实际源码结构**。追问重点是为什么不需要 CAS、怎样发布 payload、怎样安全复用槽位，以及为什么不能随意让生产者修改 tail。
