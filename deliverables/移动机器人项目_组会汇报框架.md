# 移动机器人项目组会汇报框架

> 主题：基于 ROS 的自主探索、导航与机械臂协同作业。建议按 **25 分钟汇报 + 5 分钟讨论** 准备，主线是“机器人怎样知道自己在哪、下一步去哪、到达后怎样完成作业”。

## 一、汇报目标与叙事主线

听众听完后应能回答三个问题：

1. ROS 如何让底盘、激光、定位、导航和机械臂交换数据？
2. 机器人如何从未知地图走到工作台？
3. 到站以后，系统如何保证底盘与机械臂安全地交替工作？

建议以**一次完整任务**串起知识和实现：

```text
传感器/里程计 → 建图 → 发现未知区域 → 导航 → 工位精停
                                         → 目标识别 → 机械臂抓放 → 任务结束
```

主从编队是项目的另一条能力线，放在主体流程之后讲，用一页说明其与单机探索共享的定位和通信基础。这样可避免把单机探索、编队和复合机器人仿真说成同一次实验。

## 三、预备知识应怎么讲

### 1. ROS 通信机制：从接口用途讲，不从 API 讲

先用一句话定义：ROS 把机器人软件拆成多个节点，节点通过标准消息和接口协作。随后只讲本项目使用的三种主要方式。

| 方式 | 适合什么 | 项目例子 | 为什么用它 |
| --- | --- | --- | --- |
| Topic 发布/订阅 | 持续更新的数据流 | `/scan`、`/odom`、`/imu`、`/cmd_vel`、任务状态 | 传感器和速度命令不断更新，多个节点可以订阅 |
| Service 请求/响应 | 需要立即得到接受/拒绝的短请求 | `/nav_sorting/start`、`/nav_sorting/stop`、分拣准备服务 | 适合触发动作或查询，但响应成功不代表长动作已完成 |
| Action 目标/反馈/结果 | 耗时、可取消的任务 | `/move_base` 导航目标、机械臂轨迹控制 | 能监控进度、取消目标并取得最终状态 |
| Parameter 参数服务器 | 配置而非实时数据 | 工位坐标、导航容差、超时和重试参数 | 让不同场景复用相同节点实现 |

**讲述示例**：激光雷达把扫描持续发布到 Topic；任务节点通过 Action 告诉 `move_base` 去某个工位，并等待结果；到站后通过 Service 请求分拣模块开始；各阶段再由状态 Topic 对外报告。用这一例子可自然引出后续项目架构。

建议画一张只有五个节点的简图，不展示整张 `rqt_graph`，否则听众很难抓住关键路径。

### 2. TF：回答“这个坐标到底相对谁”

建议用一个方块抓取例子说明：相机测得的是目标相对相机的位置，机械臂规划需要目标相对机器人基座的位置，而导航目标位于地图坐标系。TF 提供坐标系之间的变换；消息的 `frame_id` 和时间戳必须一致，否则会出现目标偏移或变换外推错误。

```text
map ─→ odom / odom_combined ─→ base_footprint ─→ base_link
                                                 ├─→ laser frame
                                                 ├─→ camera frame
                                                 └─→ arm links ─→ tcp_link
```

图中 `odom` 与 `odom_combined` 是不同场景的配置示意，不应在同一条实际运行链中同时写成两个连续的坐标系。建图时 GMapping 发布 `map → odom`；加载静态地图导航时 AMCL 发布该变换。实机 WheelTec 底盘配置还使用 `robot_pose_ekf` 输出 `odom_combined → base_footprint`。讲述时选一套与演示视频一致的 TF 树。

### 3. 机器人建模：URDF/Xacro、状态发布与控制

先用一张机器人结构图介绍 `link`（刚体）和 `joint`（连接及运动约束），再说明 Xacro 用参数和宏管理重复模型。底盘、激光雷达、相机、机械臂、夹爪各有安装关系，这些关系决定 TF 结构。`robot_state_publisher` 根据模型和关节状态发布运动部件变换。传感器外参错误会直接影响地图、定位和抓取结果。

这里不必逐条讲 XML 标签；聚焦三个问题：模型的几何形状是否正确、传感器装在哪里、机械臂工作时实体碰撞范围如何变化。

### 4. Gazebo：说明它在本项目里验证什么

URDF/Xacro 描述结构；Gazebo 加入重力、碰撞、传感器和驱动控制；RViz 用于观察地图、TF、规划路径与机械臂规划结果。展示同一机器人在 Gazebo 和 RViz 中的截图，并说清哪些观察来自仿真、哪些来自实机。Gazebo 的顺利抓取不能直接证明实机抓取稳定，因为摩擦、相机标定、夹爪接触和控制延迟会变化。

### 5. 导航相关功能包：按任务阶段讲

```text
未知环境：/scan + /odom → GMapping → /map
                       /map → RRT 前沿检测与筛选 → 探索目标

已有地图：map_server → /map；/scan + /odom → AMCL → map 下位姿

执行目标：目标位姿 → move_base → 全局路径 + 局部代价地图/规划器
                          → /cmd_vel_raw → 激光安全过滤 → /cmd_vel
```

讲清四个容易混淆的边界：GMapping 用来生成地图；AMCL 在已有地图上定位；RRT-Exploration 在这里负责提出“去哪里探索”；`move_base` 负责规划与执行到那个目标的移动。DWA/TEB 是不同场景可选的局部规划器，不需要在预备知识部分推导算法公式。机械臂路径由 MoveIt 规划，属于后半段作业链路，也不应和底盘的 `move_base` 混淆。

## 四、项目内容的重点取舍

**第 8–11 页是核心技术贡献**：底盘通信与里程计使机器人可控、可定位；GMapping 和 RRT 完成未知环境探索；AMCL 和 `move_base` 支撑复用地图导航。讲每一模块时使用相同的四步：输入、处理、输出、调试中遇到的问题。

**第 12 页编队单独成线**：讲主车状态广播、从车目标槽位、定位门控和失联停车。不要暗示它与机械臂任务同时运行，除非有对应演示。

**第 13–14 页突出系统工程**：任务状态机把底盘移动与机械臂动作错开。预停靠点之后还要检查工作台净距、相机视野和机械臂可达性；机械臂作业期间底盘保持静止，近场速度仍走激光安全过滤，停止需要得到确认。这比逐一罗列抓取动作更能说明系统设计。

## 六、备份页与可能被问到的问题

- **为什么建图与 AMCL 不一起启动？** 两者都可能提供 `map → odom`，需要按“在线建图”或“静态地图定位”选择模式。
- **RRT 在系统里负责什么？** 检测自由区与未知区交界的前沿；导航路径由 `move_base` 完成。
- **底盘反馈与 IMU 怎么融合？** 串口节点输出 `/odom`、`/imu`；实机配置用 `robot_pose_ekf` 融合，前提是时间戳、单位、安装方向和协方差合理。
- **为什么靠近桌子以后不直接开始抓取？** 底盘可达不等于相机看得见、机械臂够得着；要验证净距、视野和可达性。
- **底盘和机械臂能否同时移动？** 当前任务采用顺序协同，不是全身联合规划。
- **仿真结果能否迁移实机？** 架构和接口可复用，雷达、相机、工位、夹爪与安全参数需要重新标定和验证。
