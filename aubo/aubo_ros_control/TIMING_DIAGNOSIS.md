| 观测结果 | 对应下一项修改 |
|---|---|
| 生成锁等待显著，占供点周期较大比例 | 拆开最新目标快照与插补状态的所有权，缩短共享锁范围；保持停止请求的版本检查 |

| 旧视觉伺服的队列锁被实测为瓶颈 | 先定义单写入者、单读取者、清空和满队列语义，再替换为预分配SPSC队列 |

这些是后续修改条件，不表示本轮已改动相应控制逻辑。反向运动的V/A/J验证单独进行，

## 先区分三种频率

| 层 | 当前行为 | 应测指标 |
|---|---|---|
| 目标更新 | `CartesianJog::updateControlTarget`，50 Hz，IK/限速得到关节期望速度 | 更新间隔、偏离 20 ms 的误差、持锁等待与计算时间 |
| 轨迹点 | `generate/interpolatePoint`，每点按 **名义 5 ms** 平滑和积分 | 点序列的速度/加速度/jerk；目标编号与生成时刻 |
| 通信 | `DirectSdkBackend::jogOutputLoop`，同一连接串行查询 MAC、生成 N 点、整批同步发送 | N、批次间隔、查询/发送耗时、观测水位、响应年龄 |

点是在补点时集中生成的，不是每隔 5 ms 的墙钟时间生成一个点。
50 个点可以在几毫秒内生成，但表示 250 ms 的名义运动。
因此计算指令序列导数用 5 ms，计算线程/网络抖动用 steady clock；二者不可混用。
项目当前按控制柜每 5 ms 消费一点设计。更改这一假设前，必须验证控制柜实际消费周期，
不能仅把 ROS 频率改成 50 Hz 而仍每次只提供一个 5 ms 点。

持续运动时必要的平均吞吐条件是：

```
平均发送点数 / 平均批次间隔 ≈ 200 点/s
一轮耗时 = MAC查询 + 等待额度/调度 + 生成 + SDK发送 + sleep
```

4 点/20 ms 对应 50 次发送/s，8 点/40 ms 对应 25 次/s，
20 点/100 ms 对应 10 次/s。它们仅是相同名义吞吐的例子，不是已确定的最佳设置。
当前批次大小可变，不能把所有批间隔偏离 5 ms 都称为调度抖动。
应同时报告批间隔分布、N、`间隔 - 上一批 N×5ms` 的供需差，以及实际水位。
供需差也不代表已经测得控制柜消费量。

降低 RPC 频率可能减少同步调用开销，但增大批次/前瞻也会增加停止、反向的响应距离。
选择参数要同时满足延迟尾部覆盖和可接受的响应时间，不能只追求水位高。
若所需抗抖缓冲超过允许的停止前瞻，应调整通信或控制结构，不能只放宽看门狗。

## 当前究竟在哪里排队

```
接收 Twist -> 最新目标覆盖 -> 50Hz 更新关节目标
                                    |
SDK线程: MAC查询 -> 按需生成 N 个点 -> 本地 vector 批次 -> 同步SDK调用 -> 控制柜MAC
```

当前点动的 `unused_queue_(2)` 不承载轨迹；`setPointGenerator` 绕过 `CommandQueue`。
每点的“入队/出队”在这条路径上是 **不适用**，不能伪造时间戳。
需要测的是生成完成到加入本地批次、批内等待到 SDK 调用、调用等待，以及柜内排队。
SDK 返回成功只表示接口返回，不能作为控制柜入队或执行完成的时间戳。

MAC 原始数值的单位是标量，六轴一点；300 标量=50点=250 ms 名义覆盖。
当前目标 300、限额 360 标量，发送预算 100 ms、诊断/反馈看门狗 150 ms，本轮均未更改。
诊断没有硬件采样时间戳/执行点号，可能读到缓存。应保存每次查询起止，
以及该观测用于哪个批次；“发送前/后的 MAC”分别是前一个/后一个查询观测，
不是 SDK 调用边界处的真实瞬时水位。

判断长期低水位至少要有持续运动阶段的完整观测分布，并单列启动零、首次非零、
稳态和停止尾段。每次采样等权的比例不等于时间占比，查询慢时恰好存在观测盲区。
不能用目标设置为 50 点就断言始终还有 250 ms 余量。

## 可选采集：本轮增加的内容

默认关闭，设置 `timing_trace_path` 才启用，仅用于SDK点动。
初始化预分配200000条事件（约数十MB），使用原子索引分配独占记录槽；

| send_begin/end | 批次号、SDK调用编号、N、起止/返回码、关联查询号 |
| query_begin/end | 查询编号、起止/返回码、原始MAC标量数，包括停流后才返回的响应 |

`point.command_id` 是生成时最近接受的输入；真正用于目标更新的输入编号见关联 target。

输入ROS时间戳和steady时间是不同时间域，禁止直接相减。
记录已接受的输入，不代表捕获了网卡到ROS回调之前的所有消息排队。

## 固定排查顺序

1. 保存版本、配置、负载、动作参数、运行时间。先做禁用等待采集，看无运动时诊断/反馈长尾。
2. 在明确的单次动作范围内采集启动、持续、停止；只改一个因素。将MAC首次确认前的零与稳态零分开。
3. 首先核对点号/批号/返回是否完整、记录是否溢出。检查生成到发送延迟是否持续增长、批内等待是否增长。
4. 对照生成锁等待、计算、查询RPC、发送RPC、批间隔的P50/P95/P99/最大值，定位主耗时层。
5. 用每批前后MAC观测画水位与响应年龄；联合查看SDK长尾，判断是否仍有可观测余量。
   尾部时延不能由均值覆盖；不能把两个单项P99相加就称为整轮P99。
6. 只有证据显示瓶颈后才调整一个参数或一个环节。发送频率候选要同时检查吞吐、最低水位、停止延迟。

## CommandQueue 能否直接换SPSC无锁队列

现有mutex/deque保持了以下额外语义：

- push满时由生产者删除最旧元素，这会修改通常由消费者拥有的读位置。
- 使能、reset、动态调参、状态转换、目标距离保护、hybrid路径都会clear；
  ROS有3个spinner线程，部分操作虽受control_mutex串行化，目标距离保护clear还有独立调用路径。
- condition_variable只有notify，没有任何wait；它不是SDK阻塞等待的来源。
- 常规视觉伺服controlLoop/hybrid生成点，SDK或Gazebo二选一消费；启动阶段SDK也会预装保持点。

所以不能直接用“单push/单pop”的无锁容器替换并让其它线程继续clear或推进读指针。
若后续数据证明这里是瓶颈，可用预分配环形队列，但需先把消费者读位置的修改集中到消费者，
通过epoch/丢弃请求处理clear，定义满时拒绝/覆盖策略及未发送轨迹的连续性，验证停止语义。
最新目标可采用覆盖式邮箱，但完整平滑点序列不能任意丢中间点而还宣称jerk连续。
旧SDK视觉伺服的optimize会再次限速度、加速度；它没有点动VelocitySmoother的jerk保证。
当前点动没走这个队列，现有长等待证据在SDK响应阶段，换它不能解释或修复当前故障。

## 从 −X 转向 +X 时，加速度如何变化

期望笛卡尔速度可跳变；关节位置和已经积分的速度状态不因此重置。
当前点动把新的关节期望速度送入每轴 `VelocitySmoother`：

```
r[k] = r[k-1] + clamp(v_target-r[k-1], -A*h, A*h)
v[k] = v[k-1] + alpha*(r[k]-v[k-1])
q[k] = q[k-1] + v[k]*h
alpha = min(1, J*h/(2*A)), h=0.005 s
a[k] = (v[k]-v[k-1])/h
jerk[k] = (a[k]-a[k-1])/h
```

这是斜率限制加一阶滤波，不是时间最优S曲线。a是受限r斜率的滤波输出，
而 `|Δa| <= 2*A*alpha <= J*h`；从零初态得到离散序列的V/A/J界。
jerk有界不代表jerk自身连续（没有snap约束）。

| 参数/每点上限 | 前三轴 | 后三轴 |
|---|---:|---:|
| V (rad/s) | 0.25 | 0.35 |
| A (rad/s²) | 0.60 | 0.80 |
| J (rad/s³) | 8 | 12 |
| 最大位置增量 Vh (rad) | 0.00125 | 0.00175 |
| 最大速度增量 Ah (rad/s) | 0.003 | 0.004 |
| 最大加速度增量 Jh (rad/s²) | 0.040 | 0.060 |
| alpha | 0.03333 | 0.0375 |

上层改成50 Hz不改变这些5 ms增量。不能对每个5 ms点套20 ms的增量额度。
V先由实际任务速度、关节限制与奇异位形约束；A决定制动距离与负载能力；
J决定加速度变化快慢。缺少负载和实机导数数据，不能宣称当前值就是最优/最终值。
先固定它们作为基线，测停止距离与真实跟随，再按一个变量一次的顺序调节。
提高A但保持J不变会减小alpha，不能简单推断整个响应一定更快。

离线探针直接调用生产平滑器，以接近−V匀速后在2秒切到+V，在5秒发零。
前三轴速度在反向命令后约0.555秒过零，仍沿旧方向积分约0.08147 rad；
后三轴约0.560秒、0.11394 rad。这是满关节速度示例，不是10 mm/s的TCP动作结论。
